III.2  ·  Pattern 1 of 3
SE Project · Team 6
Repository · creational/structural · GoF
Hide storage behind an interface
// repository/ticket.repository.ts export interface ITicketRepository { create(t: Ticket): Promise<Ticket>; findById(id: string): Promise<Ticket | null>; findAll(): Promise<Ticket[]>; update(t: Ticket): Promise<Ticket>; }
// repository/in-memory-ticket.repository.ts @Injectable() export class InMemoryTicketRepository implements ITicketRepository { private store = new Map<string, Ticket>(); async create(t: Ticket) { ... } }
WHY
Business logic must not depend on storage details. Tomorrow we swap the in-memory map for PostgreSQL by changing one line in app.module.ts.
PROOF
grep -r 'InMemory' src/service/
→ zero matches. DIP enforced at the file level.
MODULE WIRING
providers: [
  { provide: 'TICKET_REPOSITORY',
    useClass: InMemoryTicketRepository }
]

III.2c  ·  Pluggable Storage
SE Project · Team 6
In-memory today · any database tomorrow
Swap the storage in one line
// app.module.ts — env-driven repository binding const useSqlite = process.env.DB_DRIVER === 'sqlite'; @Module({ providers: [ { provide: 'EVENT_REPOSITORY', useClass: useSqlite ? SqliteEventRepository : InMemoryEventRepository }, { provide: 'TICKET_REPOSITORY', useClass: useSqlite ? SqliteTicketRepository : InMemoryTicketRepository } ] })
// Local dev / tests → DB_DRIVER unset → in-memory Map // Production (Render) → DB_DRIVER=sqlite → better-sqlite3 // writes to /var/data/eticketing.db // (Render's persistent disk) // Adding PostgreSQL = one new class + // one switch arm. Service layer never moves.
WHY THIS WORKS
Services depend only on ITicketRepository. Replacing the implementation cannot break anything because nothing in src/service/ references the in-memory class.

III.3  ·  Pattern 2 of 3
SE Project · Team 6
Factory · creational · GoF
One method, polymorphic return type
// factory/event.factory.ts @Injectable() export class EventFactory { createEvent(dto: CreateEventDto): Event { switch (dto.type) { case EventType.CONCERT: return new ConcertEvent(dto); case EventType.CONFERENCE: return new ConferenceEvent(dto); case EventType.SPORTS: return new SportsEvent(dto); } } }
WHY
Constructor-soup is brittle. The Factory centralizes "how to instantiate the right subclass" so the rest of the codebase only sees an Event.
OPEN/CLOSED
Adding a WorkshopEvent = one new class + one switch arm. No service or controller is touched.
USED BY
EventService.create(dto) calls the factory and persists through the repository.
III.4  ·  Pattern 3 of 3
SE Project · Team 6
Strategy · behavioural · GoF
Same interface, three swappable algorithms
// strategy/ticket-code.strategy.ts export interface ITicketCodeStrategy { generate(): string; } @Injectable() export class UuidCodeStrategy implements ITicketCodeStrategy { generate() { return randomUUID(); } }
// service/ticket.service.ts — usage constructor( @Inject('TICKET_CODE_STRATEGY') private codeStrategy: ITicketCodeStrategy ) {} async generate(eventId) { const code = this.codeStrategy.generate(); ... }
THREE STRATEGIES
Uuid — RFC 4122 v4
Short — 8-char alphanumeric
Numeric — 6-digit code
SWAPPABLE
Change one binding in app.module.ts and the entire app generates a different code style. TicketService never changes.
FUTURE
Add ExpiringCodeStrategy for time-bound codes — zero changes elsewhere.
III.5  ·  Clean Code
SE Project · Team 6
Five principles, five concrete examples
SOLID — proven at the file level
S
Single Responsibility
Repository persists. Service decides. Controller adapts HTTP.
O
Open / Closed
New event type or strategy = add a class, never edit existing service.
L
Liskov Substitution
Concert / Conference / Sports honour Event's contract identically.
I
Interface Segregation
IEventRepo and ITicketRepo are separate; no fat interface.
D
Dependency Inversion
Service depends on interfaces only. grep InMemory src/service/ → 0
CLEAN CODE AUDIT
Meaningful naming. Functions under 20 lines. No duplication. No magic numbers. Every public method has a JSDoc summary. Result: 0 SOLID violations · 0 ESLint errors · 0 TypeScript errors.

LESSONS LEARNED
1. Architecture first, code second.
Time spent on the SRS and UML in Sprint 1 paid off ten-fold in Sprint 3.

2. Interfaces make SOLID visible.
A grader can read why the codebase is SOLID just by opening the folder tree.

The whole point is the ability to swap implementations.

VII.2  ·  Q&A
Speaker reference · do not read aloud
Anticipated questions — Part 1 of 2
If the doctor asks…
Q1Most expected
Why didn't you use a real backend or a real database?
A — The assignment asked us to mock storage in-memory behind the Repository pattern. The architecture is built so that swapping to PostgreSQL, MongoDB, or any other store is a one-line change in app.module.ts. We chose to invest time in patterns and SOLID rather than DB setup. The PostgreSQL adapter is the first item in our Enhancement Backlog. — Mahmoud
Q2Repository
What is the Repository pattern and why did you use it?
A — An abstraction over data persistence. It hides storage details behind an interface so business logic doesn't depend on RAM, SQL, or a cloud service. Required by the assignment, satisfies DIP, and makes future migrations cheap. — Ali
Q3Strategy
Why three Strategy implementations?
A — To prove the pattern, not because the system needs three. UUID for global uniqueness, Short for human-friendliness, Numeric for fast manual entry. Adding a fourth (e.g. ExpiringCode) costs zero edits to TicketService. — Ali
Q4SOLID — DIP
How do you prove Dependency Inversion?
A — Two ways. (1) Run grep -r 'InMemory' src/service/ — returns nothing. (2) Every service test injects a mock repository through Jest — only possible if the service depends on the interface. — Amr
Q5SOLID — LSP
Show LSP in your code.
A — Open the class diagram. ConcertEvent, ConferenceEvent, SportsEvent all extend Event. The repository stores them as Event; the service operates on them as Event. Each respects the constructor and decrementCapacity contract. — Amr
Q6Testing
What is your test coverage?
A — 46 unit tests. Repository layer 100%, service layer ≥ 80%. Every service test mocks its repository — the act of mocking proves DIP is wired correctly. — Seif
VII.3  ·  Q&A
Speaker reference · do not read aloud
Anticipated questions — Part 2 of 2
If the doctor digs deeper…
Q7Tech Stack
Why NestJS instead of Express or Spring?
A — NestJS gives us first-class DI tokens, modular architecture, and Swagger generation out of the box. It maps the patterns we needed (Repository, Factory, Strategy) directly onto the framework. Spring would also work — NestJS is the JS-native equivalent. — Ali (Backend)
Q8Patterns Scope
Where is the Observer pattern?
A — De-scoped intentionally. The assignment requires 2–3 patterns; we delivered three deeply rather than four shallowly. Observer is the first architectural item in the Enhancement Backlog — natural fit for ticket lifecycle notifications. — Ali
Q9Agile
How did you manage Agile in a student team?
A — Scrum with four 1-week sprints. Every sprint had a plan, daily standup, review, and retrospective documented in Notion. Every PR referenced a SET-T issue key. The Notion workspace doubles as a Jira-style backlog with Epics, Stories, Tasks, and saved views. — Mahmoud (Scrum Master)
Q10TypeScript / DI
Why interfaces if TypeScript erases them at runtime?
A — NestJS solves this with provider tokens — we bind the symbol 'TICKET_REPOSITORY' to a concrete class in the module. The injection works at runtime even though the interface is compile-time only. — Ali
Q11Retrospective
What would you do differently?
A — Two-hour architecture kickoff on Day 1; pair-programming rotation from Day 1; reserve the last day exclusively for demo polish. We logged each in our final retrospective. — Mahmoud
Q12End-to-End Flow
Walk through a single use case end-to-end.
A — UC-3 Generate Ticket. Admin POSTs to /events/:id/tickets. Controller validates DTO. TicketService calls EventFactory + ITicketCodeStrategy. Repository stores. 201 returned with the ticket URL. Three patterns visible in one HTTP call. — Amr
